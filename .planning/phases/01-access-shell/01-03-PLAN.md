    File contents:

    ```typescript
    import { auth } from "@/lib/auth";
    import { headers } from "next/headers";

    export async function POST() {
      const session = await auth.api.getSession({ headers: await headers() });

      if (!session) {
        return Response.json({ error: "Unauthorized" }, { status: 401 });
      }

      if (session.user.role !== "admin") {
        return Response.json({ error: "Forbidden" }, { status: 403 });
      }

      // Phase 1 stub — Phase 2 will replace this with real import orchestration.
      // The Phase 2 author should preserve the 401/403 gates above.
      return Response.json({ message: "Import queued" }, { status: 202 });
    }
    ```

    Rules:
    - The handler MUST be POST only — do NOT export GET (defence: prevents accidental GET-triggered side-effects, even though the stub does nothing).
    - Order matters: check session FIRST (401), then role (403). The opposite order leaks information (a 403 would imply "you're signed in but not admin", revealing session presence to an unauthenticated probe).
    - Use `await headers()` from `next/headers` — Pitfall 3.
    - Do NOT use Zod here — the stub takes no body. (Phase 2 can add input validation if/when the import accepts options.)
    - Add no extra logic, side effects, or logs in this plan. The whole point of a stub is its smallness.
  </action>

        setIsRunning(true);

          if (res.status === 202) {
            toast.success(body.message ?? "Import queued");

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Elevation of Privilege | POST /api/import called by non-admin | mitigate | Two-layer enforcement: (1) Server Component dashboard hides the Card for non-admins so the button isn't reachable from the UI; (2) API route returns 403 if `session.user.role !== 'admin'`, independent of UI gating (defence in depth) |
| T-03-02 | Spoofing | POST /api/import called with no session | mitigate | 401 returned if `auth.api.getSession()` returns null. Gates ordered session-first so unauthenticated probes don't receive 403 (account-existence leak) |
| T-03-03 | Tampering | Forged Cookie header on curl | mitigate | Better Auth validates the session token against the DB-stored `session` row on every `auth.api.getSession()` call — forged tokens don't match a real session |
| T-03-04 | CSRF | Browser-issued POST /api/import | mitigate | Better Auth's session cookie is `SameSite=Lax` by default; for state-changing POSTs from same-origin the cookie is sent automatically. Phase 1 has no cross-origin posting surface. RESEARCH.md §Known Threat Patterns notes Better Auth's built-in CSRF protection on auth endpoints; for custom routes the session-row check on every request is the primary control |
| T-03-05 | Repudiation | Admin triggers import | accept | Phase 1 stub is no-op; Phase 2 must add request logging (out of scope here) |
| T-03-06 | DoS | Repeated POSTs from a logged-in member (always 403) | accept | 4-user app; no rate limiting in Phase 1 (RESEARCH.md notes the rate-limit plugin is deferred); 403 returns quickly with minimal DB work |
| T-03-07 | Information Disclosure | 403 vs 401 distinguishability | accept | Returning 401 vs 403 reveals "you are signed in but unauthorised" vs "you are not signed in". This is the conventional HTTP semantic and is acceptable for an internal 4-user app — RESEARCH.md doesn't flag it. Phase 2 can collapse to a single 404-style response if external use ever happens |
</threat_model>
